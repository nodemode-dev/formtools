# HASHOUT_LOG · frontend/src/ui/docview

## v0.4.0 · 2026-11-03 · documents viewer

- `DocViewer` (index.ts) owns one panel per kind (text, markdown, csv, json, sqlite, pdf, font, hex, archive, checksum), each built on first use and kept. Opening another file reuses the nodes; a kind change swaps panels only after the new file has loaded, so the old panel stays up and nothing blanks. The top spinner goes through `delayedIndicator`.
- Kind choice (`docKindOf`): type pdf, font, archive first; then by extension (md, csv/tsv, json/jsonl/ndjson/geojson, sqlite/db); then type text; anything else opens as hex. `DocViewer.handles(entry)` says which entries the lead should route here.
- Hex and Checksums are offered for every file through the segmented control (keys H and K). Mode resets to the main view when the file changes. Kinds opened for the previous file are closed to free memory.
- Large data: `vlist.ts` keeps a fixed pool of row nodes and positions them with transforms; the body height is reserved for the full count. Past 8,000,000 px the scroll position maps proportionally to the row index instead of 1:1, because browsers cap element height (a 1 GB file is 67 million hex rows). `grid.ts` (sticky header, column widths set once per load) serves CSV and SQLite; hex and archive use the list directly.
- CSV reads 5,000 rows from the engine; sort and filter run in the window on that slice. The first row can be toggled between header and data.
- SQLite pages of 200 rows are fetched on demand and kept (40 pages); a table switch fetches page 0 first, then swaps header, count and widths in one step.
- Text: lines are built in chunks of 400 with `content-visibility: auto`; line numbers come from `::before` and `data-n`, so wrapping keeps them aligned. Above 20,000 lines highlighting is skipped and the note says why. Highlighted HTML is split into per-line strings that re-open the spans that cross a line break. Find marks the line and, where `CSS.highlights` exists, the exact match.
- highlight.js core and each language load by dynamic import (`highlight.ts`); markdown-it loads on first Markdown file; pdf.js and its worker (`?url`) load on first PDF. Markdown runs with `html: false`; link clicks only copy the URL; images with a scheme are replaced by their alt text, relative images resolve to `/api/file/raw` beside the file.
- JSON has no engine endpoint: the tree parses `/api/text` output (so files over 2 MB, or invalid JSON, show the Text tab with the reason). Children render on first expand, 100 at a time.
- PDF: page boxes are reserved from page 1 and corrected as each page is first seen (scroll anchoring is off, so corrections only move the pages below). Pages render into a fresh canvas and swap in, so zoom never shows a blank page. Canvases of pages far from the view are released. Text selection and in-PDF search are not built.
- pdf.js is given `cMapUrl`, `standardFontDataUrl` and `wasmUrl` under `/pdfjs/`; the lead must copy `node_modules/pdfjs-dist/{cmaps,standard_fonts,wasm}` to `frontend/public/pdfjs/` for CJK text, non-embedded standard fonts and JPEG 2000.
- Fonts: loaded with `FontFace` from the raw file URL under a fresh family name per file (the old face is removed). Collections cannot be previewed; details still show. The glyph grid lists only covered characters, found by measuring each character against two different fallback fonts; it needs a Unicode block range, so only the blocks in `blocks.ts` appear in the selector.
- Archives: the tree is built from `member` paths (folders are synthesised when the engine lists only files). Preview covers images and text only (at most 64 MB, text cut at 200,000 bytes); `openInViewer` is kept in the deps for opening extracted files later and is not called yet. Extract jobs pass no `dest` unless given.
- Checksums: hashing runs as a job and the result rows are filled in place; the pasted value is reduced to its first hex run, so lines copied from a `sha256sum` file work.
- Icons (`icons.ts`) are original line drawings merged into `ICONS`, like `ft-icons.ts`.
