## 2026-11-13 · v0.6.4 · the wait for the engine's port line ends after a minute

`src/main.rs` :: `read_port`, `PORT_WAIT` · a 60 s timer thread sends on an async channel and `std::future::poll_fn` polls the timer and the engine's output lines together; a timeout returns None, which leads to `engine_failed`. Before, an engine that stayed alive without printing its port left the splash up for ever, because no window existed yet to arm the other fallback. No new crate: the tokio that tauri brings has no time feature. Checked with `cargo check` on a scratch copy and a scratch program with the same code; not run in the app.

## 2026-11-12 · v0.6.3 · the deb's engine folder is /usr/lib/FormTools

The bundler puts resources under `usr/lib/<productName>`, and the product name became `FormTools` in 0.6.1, so the engine installs to `/usr/lib/FormTools/engine`. Earlier entries below that say `/usr/lib/formtools` describe the layout before the rename. The thumbnailer entry (`backend/app/tools/desktop/formtools.thumbnailer`) now names the new folder. The main binary is still `/usr/bin/formtools`, because the binary name comes from the Cargo package name.

## 2026-11-03, v0.2.0, desktop shell scaffold

Ported from formvis (Apache-2.0) `src-tauri`, re-read from the v1.98.7 source rather than the v1.96.4 maps. No code comments are kept in the Rust files; the context lives here.

### What the shell does

- `main()` calls `reveal::mark_launch()` first. Setup rounds the splash (`reveal::round_splash`), queues launch file arguments, then either uses the dev engine or spawns the engine with `FORMTOOLS_PORT=0` and reads the port from the `http://127.0.0.1:PORT` line on stdout.
- Engine program: macOS runs `Resources/engine/formtools-engine` by path (also `engine/` beside the binary in `tauri dev`), every other OS runs the sidecar `formtools-engine`.
- Dev: in a debug build, `FORMTOOLS_DEV_URL` (when it starts with `http://127.0.0.1:` or `http://localhost:`) is used as the page URL and no engine is spawned; any other non-empty value means `http://127.0.0.1:8240`.
- Main window: external URL, title `formtools`, hidden on macOS until `app_ready` (alpha 0 on screen meanwhile), background `#0a0a0a`, 90 percent of the screen or the saved size, minimum 980 by 640, drag-drop handler off, overlay title bar and hidden title on macOS with the lights placed in the 38 px row.
- Timing: `SPLASH_MIN` 2600 ms, `BAR_FINISH` 220 ms, `FALLBACK` 20 s. The splash hook is `window.formtoolsSplashDone()`.
- Engine failure (no spawn, early exit, no port, window build error): the splash closes, a dialog says the engine failed, the engine is stopped and the app exits with code 1.
- Single instance: a second launch passes its existing file or folder arguments to the running window as an `open-paths` event (payload: array of path strings) and focuses the window. Launch arguments and macOS `RunEvent::Opened` paths are queued and emitted 800 ms after the first page load finishes, so the page has registered its listener.
- Commands: `app_ready`, `text_edit`, `pick_folder(title?)`, `pick_files(title?, extensions?)`, `reveal_in_folder(path)`, `open_with_default(path)`. `reveal_in_folder` uses the opener plugin's `reveal_item_in_dir` (Explorer select on Windows, Finder reveal on macOS, the file manager's ShowItems over D-Bus on Linux with a folder fallback).

### Removed relative to formvis

- Native GPU renderer, fonts, display profile, recent documents, updater commands, exit gate and quit confirmation, crash-loop page, interface zoom, `set_window_title` command, launch-time `--command` and `--script` flags, `mcp` and `agents` command-line modes, Linux AppImage integration, portable and data-folder arguments, display server and graphics backend switches, file associations, wix fragment, deb template. None are in the contract.
- Dependencies dropped: devtools feature, fontdb, x11-dl, webkit2gtk, gtk, windows-sys, formvis-render, objc2 `NSDocumentController`.
- Window state keeps size, position and maximised state only (no zoom). On macOS a dead web content process is reloaded; there is no crash-loop page.
- The page sets its title with the `core:window:allow-set-title` permission; the lights are placed again on resize, focus, theme and scale events and on page load.

### Config notes

- `bundle.resources` for a `licenses` folder is left out because the folder does not exist yet; add `"resources": { "../licenses": "licenses" }` (and the same key beside `engine` in `tauri.macos.conf.json`) when it does.
- Updater: `pubkey` empty and `endpoints` empty; formcompiler fills both in at release time.
- No `fileAssociations` (not asked for in the contract).
- Dependencies use semver majors in `Cargo.toml`; `Cargo.lock` holds the exact resolved versions.

### Icons

`assets/formtools-icon.svg` is an original design (dark rounded square, gradient lens ring, short diagonal handle, 2 by 2 grid inside the lens). `assets/formtools-icon-1024.png` is rendered with `rsvg-convert`, and `src-tauri/icons/*` comes from `tauri icon` (CLI 2.11.4), including the Android and iOS sets it makes.

## 2026-11-03 · v0.3.0 · the engine as a folder on every OS

- `tauri.conf.json` drops `externalBin` and ships `"resources": { "engine/": "engine/" }`. Per https://v2.tauri.app/develop/resources/ a trailing slash source copies the folder recursively with its structure, so `src-tauri/engine/formtools-engine[.exe]` and `_internal/` land under `$RESOURCE/engine/`. `tauri.macos.conf.json` is now `{}`: macOS uses the same layout, and the old override is gone. The folder must exist at build time, so `setup/freeze_backend` has to run before `tauri build` and `cargo check`.
- The resource directory per bundle type comes from https://docs.rs/tauri/latest/tauri/path/struct.PathResolver.html (resource_dir; Tauri says this is not a contract). macOS .app: `formtools.app/Contents/Resources/engine/`. Windows MSI and NSIS: `engine\` beside `formtools.exe` in the install folder. Linux deb and rpm: `/usr/lib/formtools/engine/`. AppImage: `$APPDIR/usr/lib/formtools/engine/`. Only the deb was built here; `dpkg -c` showed `usr/lib/formtools/engine/formtools-engine` next to `usr/bin/formtools`. The others follow the documentation and were not built.
- `packaged::engine_program(handle)` resolves `engine/formtools-engine[.exe]` with `BaseDirectory::Resource`, then `engine/` beside the executable, then `src-tauri/engine` from `CARGO_MANIFEST_DIR` (for `tauri dev`).
- `main.rs` no longer uses the shell sidecar API. `std::process::Command` starts the engine by path with `FORMTOOLS_PORT=0`, `PYTHONUNBUFFERED=1`, stdin closed, stdout and stderr piped and read line by line on two threads that feed the same `http://127.0.0.1:PORT` regex handshake and keep draining afterwards. Windows sets `CREATE_NO_WINDOW` (0x08000000). `kill_backend` runs on `RunEvent::Exit` and on engine failure: SIGTERM then a 1.5 s wait on `try_wait`, then `kill` and `wait` on unix; `kill` and `wait` on Windows. A hard crash of the shell (panic abort, SIGKILL) is not covered; a Windows job object would need `windows-sys`.
- `tauri-plugin-shell` stays registered because the contract lists it; nothing calls the sidecar API.
- Found while checking: `tauri build` run from `frontend/` (as `setup/desktop_build` does) stopped with "Couldn't recognize the current folder as a Tauri project", and from the repo root it stopped on mismatched versions (crate `tauri` 2.12.5 in `Cargo.lock` against `@tauri-apps/api` 2.11.1). `cargo build --release` plus `tauri bundle --bundles deb` from the repo root worked.

## 2026-11-03 · v0.5.0 · desk utilities in the shell (`src/desk/`)

- Commands (all in `build.rs` `APP_COMMANDS`, `generate_handler!`, `capabilities/default.json`): `desk_capabilities`, `desk_start(tool, options)`, `desk_close`, `desk_ocr(path, rect, lang)`, `desk_awake_get`, `desk_awake_set(req)`, `desk_topmost_toggle`, `desk_shortcuts_set(list)`. Names, arguments and result shapes match `frontend/src/io/desk.ts`. No deviation.
- Capture: Windows and macOS use `xcap` (`Monitor::all` and `capture_image`); Linux does not, because `xcap` pulls PipeWire and Wayland libraries (libpipewire-dev, clang) that this machine lacks and that Wayland would not make usable anyway. Linux reads the X11 root window with `x11rb` (`GetImage` per RandR monitor, pixel layout taken from the visual masks) and writes RGB PNGs with the `image` crate (fast compression). Files go to `<temp>/formtools-desk/<id>/monitor-N.png`; the whole `formtools-desk` folder is cleared on every start and on exit.
- Monitor geometry for the overlay windows comes from Tauri's own monitor list (physical position, size, scale); each captured image is matched to a Tauri monitor by origin, then by size, then in order. `Monitor.width` and `height` are the PNG size, `x` and `y` and `scale` are Tauri's.
- Overlay windows: `overlay-N`, external URL built from the `main` window's current URL (path `/overlay.html`, query `tool`, `shot`, `monitor`, `scale`, `options`). Built with `visible(false)`, transparent, background alpha 0, undecorated, no shadow, always on top, no taskbar entry, visible on all workspaces, then moved and sized in physical pixels. They are shown from the webview `PageLoadEvent::Finished` hook (focus only on the monitor under the pointer), with a 2.5 s fallback show. No extra `app_ready`-style command was added: the page starts transparent and draws the frozen screenshot of what is already on screen, so the first visible frame cannot flash white and the page needs no new signal. macOS raises the window level to 25 (above the menu bar). Wayland builds the timer overlay fullscreen because windows cannot be placed there.
- Capabilities: `overlay.json` for `overlay-*` with the same `http://127.0.0.1:*` remote rule and only `core:event:default`, `core:window:allow-close`, the two clipboard write permissions, `allow-desk-close` and `allow-desk-ocr`. `default.json` gained the desk commands and the clipboard write permissions (the main window copies text too). Dev origins other than 127.0.0.1 (such as `localhost`) are not matched by either rule, as before.
- OCR: `desk_ocr` refuses any path outside the capture folder, crops in Rust, then macOS Vision (`VNRecognizeTextRequest`, accurate, language correction on, lines sorted top to bottom), Windows `Windows.Media.Ocr` on a short-lived MTA thread, Linux `tesseract stdin stdout --psm 6 [-l lang]` as a child with the PNG on stdin (regions under 100 px tall are upscaled 2x or 3x first; the language code is checked to letters, digits, `_` and `+`).
- Awake: one holder behind a mutex. Windows keeps a thread alive that calls `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED [| ES_DISPLAY_REQUIRED])` (the flag is per thread); macOS creates `PreventUserIdleSystemSleep` and optionally `PreventUserIdleDisplaySleep` IOPM assertions through hand-declared IOKit and CoreFoundation externs; Linux runs `systemd-inhibit --what sleep` (or `idle:sleep` with the display) around a `sh` loop that ends when formtools or the inhibitor dies, so a crash cannot leave a lock behind. A start that fails returns the first stderr line. `timed` clamps to 1440 minutes and ends by itself; `until` is epoch milliseconds.
- Always on top: Windows `GetForegroundWindow` (skips formtools' own process) then `SetWindowPos(HWND_TOPMOST or HWND_NOTOPMOST, SWP_NOMOVE | SWP_NOSIZE | SWP_NOACTIVATE)`; Linux X11 `_NET_ACTIVE_WINDOW` then a `_NET_WM_STATE` client message (`_NET_WM_STATE_ABOVE`, add or remove by the current state), skipping a window whose `_NET_WM_PID` is ours. macOS and Wayland return `ok: false` with a sentence, never an `Err`.
- Shortcuts: `tauri-plugin-global-shortcut` `on_shortcut` per binding after `unregister_all`; a press emits `desk://shortcut` (the id string) to `main`. An empty accelerator counts as disabled and succeeds; a duplicate inside one list and a registration the OS refuses return an error sentence.
- Capability report: Linux `session` is `wayland` when `XDG_SESSION_TYPE` is `wayland` or only `WAYLAND_DISPLAY` is set, else `x11` when `DISPLAY` is set. Capture tools are unsupported on Wayland and when the X11 display cannot be opened; `text` also needs an OCR engine; `topmost` is unsupported on macOS and Wayland; `awake` on Linux needs `systemd-inhibit` on PATH; `hosts` and `env` always report ok (the engine does the work). macOS asks for Screen Recording through `CGPreflightScreenCaptureAccess` and `CGRequestScreenCaptureAccess` before the first capture.
- `Cargo.toml`: `rust-version` raised from 1.77.2 to 1.90 because `tauri-plugin-clipboard-manager` 2.5.0 needs it (2.5.0 is the version that matches npm 2.5.0). The new plugin and platform crates are added; no existing locked crate changed version.
- Checked: `cargo check` on Linux clean. `--target x86_64-pc-windows-msvc` and `--target aarch64-apple-darwin` pass only with stand-in C headers for the `ring` build script and, on macOS, `clang` for `objc2-exception-helper` (no MSVC or Apple SDK here); the Rust of the shell is type-checked against both. Functionally on Linux under Xvfb: capture wrote a 1280x800 PNG, tesseract read a region as the exact text on screen, the path guard refused `/etc/passwd`, the awake holder started, ended and reported `off` with a stand-in `systemd-inhibit` (the real one needs a D-Bus session this machine lacks and returned its error sentence), and the topmost toggle returned its no-window sentence (Xvfb has no window manager). The overlay windows, global shortcuts and the Windows and macOS code paths were not run.

## 2026-11-03 · v0.5.0 · Phase 9 in the shell (`src/osint/`, argv, associations, deb thumbnailer)

- Command line: `formtools [--tool view|convert|resize|rename|hash|dupes|disk] [paths...]`, also `--tool=<id>` and `--` (everything after it is a path). Parsed by `launch_from_args` for the first launch (setup) and for second launches (single-instance, which supplies the cwd). Other `-` arguments are ignored as before. Relative paths resolve against the second launch's cwd, or the process cwd on first launch (now made absolute, which the old code did not do). Only paths that exist are kept. A known tool emits `open-tool` with `{"tool": id, "paths": [...]}` (also with an empty list); an unknown or missing tool value falls back to `open-paths`, and paths alone keep `open-paths` unchanged. Before the first page load settles the events are queued in order (adjacent `open-paths` merge) and emitted 800 ms after it. macOS `RunEvent::Opened` still emits `open-paths`.
- Commands (`build.rs` `APP_COMMANDS`, `generate_handler!`): `osint_menu_status()`, `osint_menu_install(ids)`, `osint_menu_remove(ids?)` (no ids removes every formtools entry). All return `{supported, installed, where, reason}`; a failure keeps the real state and puts one sentence in `reason`. Install adds to what is already installed, it does not replace it. Permissions are in a new `capabilities/menus.json` limited to the `main` window (the existing `default.json` also lists `splash`, so the new commands were not put there).
- Linux (`osint/linux.rs`, files under `$XDG_DATA_HOME` or `~/.local/share`): Nautilus scripts `nautilus/scripts/formtools/<Title>` (mode 755, read `NAUTILUS_SCRIPT_SELECTED_FILE_PATHS`), Dolphin `kio/servicemenus/formtools.desktop` (mode 755, `X-KDE-Priority=TopLevel`, `X-KDE-Submenu=formtools`, one `Desktop Action formtools-<id>` each), Nemo `nemo/actions/formtools-<id>.nemo_action`. Remove deletes only those names and the `formtools` scripts folder when empty. Launch path: `$APPIMAGE` when set, else `/usr/bin/formtools` when the running binary resolves to it, else `current_exe()`. A path with quote, dollar, backtick, backslash, percent, ampersand or angle characters is refused with a sentence.
- macOS (`osint/macos.rs`): `~/Library/Services/formtools <Label>.workflow/Contents/{Info.plist,document.wflow}`; `NSServices` with `runWorkflowAsService`, Finder context, `public.item`; the Run Shell Script action takes the files as arguments and runs `nohup '<binary>' --tool <id> "$@" &`. `pbs -flush` runs after install and remove. Remove only deletes folders of that name that hold an `Info.plist`. The generated files were never opened in Automator or Finder here.
- Windows (`osint/registry.rs`, `windows` crate `Win32_System_Registry` and `Win32_Security`): `HKCU\Software\Classes\*\shell\formtools.<id>` and `...\Directory\shell\formtools.<id>` with `MUIVerb`, `Icon` and `command` = `"<exe>" --tool <id> "%1"`; remove uses `RegDeleteTreeW` on exactly those keys. Explorer starts one process per selected file, so a multi-selection arrives as several `open-tool` events through single-instance. Not run on Windows.
- File associations (`tauri.conf.json` `bundle.fileAssociations`): 66 entries, one per MIME type (the bundler writes one `mimeType` per association), all `role: Viewer`, `rank: Alternate`; groups Image, Photoshop image, OpenEXR image, Radiance HDR image, Camera RAW image, 3D model, Font, Archive, formvis project. The Linux `.desktop` entry only lists MIME types, it sets no default.
- Windows default-handler problem: Tauri's NSIS template macro `APP_ASSOCIATE` writes `HKCU or HKLM\Software\Classes\.<ext>` default to the file class (backing up the old one), which makes formtools the default handler. To honour "never the default", `tauri.windows.conf.json` empties `fileAssociations` for Windows builds, so Windows installers register no extensions. Restoring them needs a custom NSIS template that writes `OpenWithProgids` only. WiX was not inspected.
- Linux deb: `bundle.linux.deb.files` maps `/usr/share/thumbnailers/formtools.thumbnailer` to `backend/app/tools/desktop/formtools.thumbnailer`, and `bundle.linux.deb.desktopTemplate` (`formtools.desktop.hbs`) is the bundler's default desktop template plus `%F` on `Exec`, because the default `Exec=formtools` passes no file. The installed engine is `/usr/lib/formtools/engine/formtools-engine`, equal to the thumbnailer's `TryExec` and `Exec` path, so the backend file needs no change.
- Checked: `cargo check` clean (no warnings) for x86_64-unknown-linux-gnu, x86_64-pc-windows-msvc (stand-in headers plus a fake `lib.exe` for `ring`) and aarch64-apple-darwin (`-ffreestanding` stand-in headers). A probe outside the repo ran the Linux install, add, remove and remove-all against a throwaway HOME (nothing left behind but empty parent folders), parsed the `.desktop` and `.nemo_action` files with a strict ini reader (`desktop-file-validate` is not installed), ran a generated Nautilus script with two selected paths (one with a space; the arguments arrived intact), and wrote the macOS workflows on Linux and parsed all plists with `plistlib`. The deb builds with `./setup/desktop_build --bundles deb`; the extracted engine ran the thumbnailer line on a PNG and exited 0. Not run: any Windows or macOS menu code, Nautilus, Dolphin or Nemo themselves, the argv grammar inside a live window.

## 2026-11-03 · v0.6.0 · Splash and boot parity with formvis

- Audit against formvis 1.98.7 (code first, the v1.96.4 map second). With comments and the app name removed, `reveal.rs` is identical to formvis's (`SPLASH_MIN` 2600 ms, `BAR_FINISH` 220 ms, `FALLBACK` 20 s, 16 px native radius, `app_ready`, `conceal`, `show_main`); `traffic_lights.rs`, the placement half of `window_state.rs`, the `splash` block of `tauri.conf.json` (360 by 200, undecorated, centred, transparent, no shadow, hidden), `macOSPrivateApi`, the `macos-private-api` and objc2-app-kit features, `build.rs` and `capabilities/default.json` (`allow-app-ready`, window `splash` listed) match as well. `main.rs` already follows the formvis order: `mark_launch` first, `round_splash` first in setup, engine by path with `FORMTOOLS_PORT=0`, port from the `http://127.0.0.1:PORT` line, `.visible(reveal::BUILD_VISIBLE)` and `.background_color(reveal::BACKGROUND)` on the main window, `conceal` after `build()`, the splash closed only by `show_main` or on failure. No change to `main.rs`, `reveal.rs`, `tauri.conf.json` or the engine was needed.
- Kept different on purpose: the engine is a one-folder build on every OS and is started with `std::process::Command` (v0.3.0) where formvis uses the shell sidecar on Linux and Windows; the drag-drop handler stays on (the page uses Tauri's paths); no crash-loop page, zoom or `set_window_title`; the failure dialog and exit go through `engine_failed`, which also covers a dev URL that does not parse.
- Engine ready line: `formtools_engine.py` prints `INFO:     Uvicorn running on http://127.0.0.1:PORT` on stdout (uvicorn log config), which `read_port` matches. A cold one-folder engine under Xvfb was listening 0.8 s after spawn; session start work already runs in the executor (`registry.startup`), not before the server answers.
- Tried and reverted: building the main window hidden on Linux (`.visible(false)`), because the module header of formvis's `reveal.rs` says "elsewhere it is created hidden" while its constant builds it visible off macOS. Under Xvfb with WebKitGTK the page loaded and ran its scripts but `app_ready` did not arrive in 15 s: a hidden window's web view stops animation frames, so `revealApp`'s two frames never fire and only the 20 s fallback would show the window. The build stays visible off macOS, as in formvis.
- Measured (release binary from `setup/desktop_build --bundles deb`, Xvfb 1600x1000 with a D-Bus session, 2 cores, software GL, fresh HOME, a screen grab every 100 ms for 15 s, two cold runs): splash window mapped at 0.5 to 0.6 s; main window mapped at 1.4 to 1.5 s (dark, no white); splash closed at 4.4 to 4.65 s, which is the page's `app_ready` plus the 220 ms bar finish (the 2600 ms minimum had long passed). 0 frames out of 149 and 150 held a white-heavy window. Because the main window is mapped first and sits above the splash, the splash card is covered from the main window's mapping until the splash closes; in a diagnostic run that raised the splash above it, the splash showed the icon, the text and the filled bar. Xvfb has no compositor, so the transparent corners of the splash render black here; a real transparent corner was not observed.
- The `backend/venv` folder already exists as a working venv, so no symlink was made (an `ln -s` onto an existing folder would have nested inside it).
