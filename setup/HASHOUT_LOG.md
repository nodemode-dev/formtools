## 2026-11-19 · v0.9.1 · the engine carries one Python library, as a plain file, so Apple's notary accepts the app

- Fault (formtools 0.9.0 for macOS, the first build with notarization on): the app compiled and was signed, then Apple's notary answered `Invalid`, "The signature of the binary is invalid", for `FormTools.app/Contents/Resources/engine/_internal/Python.framework/Versions/3.14/Python`. No release was made.
- Cause: the same library has to be valid in two places and no single signature is. PyInstaller puts it at `_internal/Python.framework/Versions/3.14/Python` and makes `_internal/Python` a link to it. The app bundle carries the link as a second plain file, and the engine loads that plain file (the 0.8.0 fault, entry of 2026-11-14). The 0.8.1 change signed the library outside its framework so the plain file validates. The notary checks every file where it sits: at the framework path it expects a signature bound to the framework, finds one that is not, and refuses. The 0.8.1 entry said the notary had not yet seen an engine signed this way; this is what it does with one.
- `freeze_backend` :: `plain_framework_libraries` (new), called first by `sign_engine` · Now: a link outside a framework that points at a Mach-O inside a `*.framework/` folder of the engine becomes the file itself, its old signature is removed so the loop signs it alone, and that framework folder is deleted. The app then holds the library once, as `_internal/Python`, which is the file the engine loads, with a signature that is right for a plain file. Nothing else used the framework folder: PyInstaller's program asks for `Python` beside it.
- `freeze_backend` :: `sign_engine` · the in-place check no longer skips a Mach-O that is still inside a framework folder (one nothing links to from outside): it must pass `codesign --verify --strict` where it sits, or the build stops there with the reason, before the long compile and the upload to Apple.
- `--selfcheck` still runs after signing. It now starts the engine in the very layout the app carries (no link), so a library that cannot load stops the build on the runner.
- Removed from the in-place check, in full: `    [ "${f#*.framework/}" = "$f" ] || continue`.
- Checked on Linux, with stub `codesign` and `file` in which a signature holds only in the kind of place it was made for: the released script leaves a file the stand-in notary refuses at exactly the path Apple named; this one leaves every Mach-O valid where it sits, no framework folder, `Python` a real file, an ordinary link still a link; a framework nothing links to stops the build with the new sentence; an engine with no framework at all is signed as before. `bash -n`; no construct newer than bash 3.2. Not run: a macOS build, the real `codesign`, the notary. Only signed builds take this path; an unsigned local Mac build is unchanged.

## 2026-11-03 · v0.2.0 · launcher, setup scripts, CI, agent kit

- The launcher and `setup/` follow formvis's shape (bash dispatcher, `.bat` twins, `lib.sh`) with the prefix `ft_` and the root variable `FORMTOOLS_ROOT`. formvis delegates installs and boots to `oc_install` and `boot_*` files inside `backend/` and `frontend/`; formtools does the work in `setup/` itself because the contract lists no such files there.
- `install_backend` creates `backend/venv`, then installs `requirements.txt`; on macOS it prefers `requirements_macos.txt` when present. `install_frontend` runs `npm ci` and falls back to `npm install` when there is no lock file. `install --lite` is accepted and does nothing yet, so release pipelines that pass it do not fail.
- `install_desktop` needs `backend/requirements_desktop.txt` (macOS: `requirements_desktop_macos.txt` if present). The Tauri CLI comes from frontend devDependencies, so `desktop dev` and `desktop build` call `npx tauri` from `frontend/`. A relative `--config` path is therefore resolved from `frontend/`; formcompiler should pass an absolute path.
- `freeze_backend` freezes `backend/formtools_engine.py` as `formtools-engine`. The variable `FT_EXTRA_HIDDEN_IMPORTS` (filled from the environment variable `FORMTOOLS_HIDDEN_IMPORTS`, space separated) takes the hidden imports the engine agent reports. The Windows twin reads the same environment variable. `src-tauri/entitlements.plist` is used for macOS signing only when the file exists.
- The macOS signing loop is formvis's: it skips Mach-O files PyInstaller already signed with a timestamp, hardened runtime and library validation disabled, signs the rest, then verifies all of them.
- `mcp_stdio.py` starts the engine only when no `--url` or `FORMTOOLS_MCP_URL` is given: `serve` when `frontend/dist` exists, else `backend`. Set `FORMTOOLS_MCP_AUTOSTART=0` to turn that off. The bridge writes only protocol lines to stdout.
- `cli.py` has `info`, `list` and `version` only; the engine must be running.
- `ci.yml` pins actions to commit SHAs read from the GitHub release pages: checkout v4.2.2 `11bd71901bbe5b1630ceea73d27597364c9af683`, setup-node v4.4.0 `49933ea5288caeca8642d1e84afbd3f7d6820020`, setup-python v5.6.0 `a26af69be951a213d495a4c3e4e4022e16d87065`. No `${{ }}` appears inside a run script; the engine port goes through `env`.
- The plugin manifest lists only the driving skill, because the harness skill is for changing code.
- The two skills are mirrored byte for byte into `.agents/skills/`.

## 2026-11-14 · v0.8.1 · the Python library keeps a signature that survives the app bundle

- Fault (formtools 0.8.0 for macOS, the first build formcompiler made): the app showed "The formtools engine failed to start" on every launch. Run by hand, the engine printed `Failed to load Python shared library '.../Contents/Resources/engine/_internal/Python'` with `code signature invalid`, and `codesign -vvv` on that file said `invalid Info.plist (plist or signature have been modified)`.
- Cause: the runner's Python is a framework build, so PyInstaller puts the library at `_internal/Python.framework/Versions/3.12/Python` and makes `_internal/Python` a symlink to it. `sign_engine` kept a file only when it carried the `disable-library-validation` entitlement, which libraries do not, so it re-signed them all in place. `codesign` signs a file that sits in a framework as that framework's main binary, which binds the signature to the framework's `Info.plist`. In the installed app `_internal/Python` is a plain file, not a link (seen with `ls -l` on the 0.8.0 install), and a framework-bound signature does not validate on a plain copy. `--selfcheck` passed because it runs in `src-tauri/engine`, where the link is still a link.
- `freeze_backend` :: `sign_engine` · Now: (1) a Mach-O under a `*.framework/` folder is never kept and is signed as a copy in a temporary folder outside the framework, then moved back, so its signature binds to the file alone; (2) the entitlement test applies only to `formtools-engine`, the one file that needs entitlements, so libraries PyInstaller signed with the Developer ID, a timestamp and the hardened runtime are kept; (3) the in-place `codesign --verify` skips framework files, whose signatures are meant for the plain copy; (4) a guard copies every symlinked Mach-O with `cp -L` and stops the build when the copy fails `codesign --verify --strict`, which is the fault above caught at build time.
- Removed from the keep test: `&& codesign -d --entitlements - "$f" 2>/dev/null | grep -q 'com.apple.security.cs.disable-library-validation'` as a condition on every file. Removed: the single `codesign --force --timestamp --options runtime "${sign_args[@]}" --sign "$APPLE_SIGNING_IDENTITY" "$f"` for every file, now split by whether the file is in a framework.
- The entry of 2026-11-03 calls this loop formvis's. Any app that copied the loop and ships a one-folder engine from a framework Python has the same fault.
- Checked: `bash -n`, and `sign_engine` run against a stand-in engine folder with stub `codesign` and `file` (the framework library signed outside its folder, a PyInstaller-signed library kept, ad hoc and unsigned ones signed, the engine program signed with entitlements, the guard stopping on a framework-bound signature). Not run: a macOS build. Apple's notary service has not seen an engine signed this way, because notarization is off while formcompiler's `signing.macos` is `developer-id`.
